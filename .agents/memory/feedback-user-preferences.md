# 使用者偏好

## 溝通
- 使用者問「A 好還是 B 好」這類問題時，先回答並等使用者決定，不要直接動手做（2026-11-11：一開始沒等回答就寫檔，被擋下來）。
- 需求會在過程中陸續補充，補充的內容以最新的為準。
- 使用者不開 IDE，也沒有裝 Android Studio、Unity 等工具；要執行的東西都要能在根目錄點兩下啟動。
- 背景執行的程式（測試用伺服器）用完要關掉。

## 遊戲設計要求（2026-11-11 使用者指定）
- 在手機上玩，橫放。
- 手排：6 速 + R。離合器在左手；排檔、煞車、油門在右手（排檔在煞車油門上方）。左手踩離合器、右手換檔要同時做。
- 離合器、油門、煞車都是「按得越靠上踩得越深」。
- 離合器要像一般手排車：自己慢慢放才能平順前進，放太快要頓一下（甚至熄火）。
- 左駕（駕駛座在左）。方向盤用旋轉手機操控。
- 要有左、右後照鏡（放在畫面左上、右上）和圓鏡（位置由我方決定，目前放在右後照鏡左邊，照車門側）。
- 聲音盡量接近真實開車。
- 路況、道路、號誌、交通規則盡量跟台灣實際情況一樣；車輛操作以使用者在駕訓班開大客車的經驗為準（例如圓鏡照車頭、煞車踏板比油門大）。使用者提到「駕訓班是這樣」時照做（2026-11-12）。
- 手機會發燙是使用者在意的問題，新增畫面效果前先考慮效能。
- 參考對象是市面上的公車模擬遊戲的「玩法」，但內容必須原創：不照抄任何現有遊戲的名稱、車款、地圖、美術。

## 功能要對應真實情況（2026-11-12 使用者要求寫進記憶）
- 之後新增或修改的功能，行為都要對應真實情況（真的大客車、台灣的道路與交通規則）。
- 我自己提議或設計的功能：直接照真實情況做，並說清楚依據是查到的還是估的。
- 使用者提出的做法：先說明真實情況是怎樣、和他提的差在哪，等使用者決定要「照真實」還是「照他說的」，再動手。不要為了迎合使用者的直覺先做出不真實的版本，也不要自己替使用者的說法加上真實情況沒有的限制。
- 起因：同一天有兩次先做了不真實的版本再重做——使用者以為在檔位上放油門車會一直慢到停，我照做把怠速調弱，後來才改回真車的行為；使用者說「要先回 N 才能進 R」，我自己加了「要放手再拖一次」，使用者問了才改成真車的擋塊。

## 程式與檔案慣例
- 程式要分檔，不要全部塞在一個 html。
- 用到的函式庫要放在專案目錄內，不要依賴全域或 npx 快取。目前 Three.js 直接放在 `lib/`（為了 GitHub Pages），沒有 `node_modules`。
- 與專案無關的檔案可以刪。
- 檔案格式、記憶與工作日誌的規則比照 alms 專案，見 `AGENTS.md`。網頁的 description 與 og 標籤也比照 alms（og:image 用絕對路徑）。
- css 的 @media 盡量用 min-width（由小螢幕往大螢幕寫），沿用 alms 的慣例；目前唯一的例外是「直放時顯示請橫放」用 orientation 判斷。
